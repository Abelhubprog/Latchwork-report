1. Introduction to Latchwork

Type Purpose User State
Tutorials Learning-oriented lessons that take users through practical experiences Studying - needs guidance

Reference Information-oriented technical descriptions for accurate usage Working - needs facts

Latchwork is a paid-actions network designed for autonomous agents that need to interact with slot-scarcity and paperwork-heavy portals. It addresses the fundamental challenges of automating tasks on websites that were never designed for programmatic access, such as visa appointment systems, healthcare scheduling portals, government compliance sites, and financial onboarding (KYC) platforms.

Core Problem:Traditional automation tools (RPA, browser automation) fail in high-stakes scenarios because they lack trust mechanisms, proof-of-execution, and economic incentives. When an agent books a visa appointment or submits a government form, how do you know it actually succeeded? How do you resolve disputes? How do you handle payments?

Key Primitives

  • Native Micropayments (HTTP x402): Agents can pay for access, prioritize requests, and handle paywalled resources programmatically
  • Deterministic FSM Execution: State machine-based workflows ensure predictable, replayable, and verifiable agent behavior
  • Monitor-Commit Coalescing: Efficient resource usage by separating lightweight monitoring from expensive commit actions
  • Human-in-the-Loop Gates: Graceful handling of CAPTCHAs, approvals, and exceptional cases requiring human judgment
  • Proof-of-Execution Artifacts: Cryptographically verifiable logs, screenshots, and state transitions for audit and dispute resolution
  • Trust Layers: Staking, validation, and insurance mechanisms to align incentives and guarantee outcomes
  • Session Isolation: Secure, ephemeral execution environments that prevent data leakage and unauthorized access

2. Tutorials

Learning-oriented lessons that guide you through practical experiences with Latchwork

2.1 Getting Started with Your First Agent

Prerequisites: Node.js 18+, Git, basic JavaScript knowledge

In this tutorial, you'll create your first Latchwork agent that monitors a website for changes and takes action when specific conditions are met. By the end, you'll understand the core concepts of agent configuration, state management, and execution.

Step 1: Install the Latchwork CLI

npm install -g @latchwork/cli

Step 2: Initialize a New Project

latchwork init my-first-agent cd my-first-agent npm install

This creates a project structure with:

  • agent.yaml - Main configuration file
  • src/ - Source code directory
  • tests/ - Test files
  • docs/ - Documentation folder

Step 3: Define Your Agent Configuration

Edit agent.yaml to define your agent's behavior:

name: website-monitor version: 1.0.0 description: Monitor example.com for changes states: - id: idle type: initial - id: checking action: fetch config: url: https://example.com/status method: GET - id: analyzing action: evaluate config: condition: response.status == 'available' - id: notifying action: webhook config: url: https://my-app.com/webhook payload: message: 'Slot is available!' transitions: - from: idle to: checking trigger: interval config: seconds: 60 - from: checking to: analyzing trigger: complete - from: analyzing to: notifying condition: result == true - from: analyzing to: idle condition: result == false

Step 4: Run Your Agent Locally

latchwork run --watch

The --watch flag enables live reloading. As you edit agent.yaml, the agent will restart automatically.

Step 5: Verify Execution

Open the Latchwork dashboard at http://localhost:3000 to see your agent's execution trace, state transitions, and logs.

2.2 Creating a Slot-Monitoring Agent

Prerequisites: Completed Tutorial 2.1, Playwright basics

This tutorial builds on the basics to create a more sophisticated agent that monitors a visa appointment portal for available slots and automatically books when one opens. This demonstrates the monitor-commit pattern that is central to Latchwork's efficiency.

Understanding the Monitor-Commit Pattern

The key insight is that checking for slot availability is cheap, but booking is expensive (requires form filling, payment, etc.). Latchwork separates these concerns:

  • Monitor Phase: Lightweight, frequent checks (every few seconds)
  • Commit Phase: Full execution only when conditions are met
  • Coalescing: Thousands of checks can result in a single commit

Agent Configuration

name: visa-slot-monitor version: 1.0.0 description: Monitor and book visa appointments # Monitor phase - lightweight checking states: - id: monitor type: initial action: browser.check config: url: https://visa-portal.gov/appointments selector: '.slot-availability' extract: text - id: evaluate action: condition config: expression: extract.includes('Available') # Commit phase - full booking workflow - id: login action: browser.fill config: selectors: '#username': '{{secrets.username}}' '#password': '{{secrets.password}}' submit: '#login-btn' - id: select-slot action: browser.click config: selector: '.available-slot:first' - id: confirm action: browser.click config: selector: '#confirm-booking' - id: capture-proof action: screenshot config: selector: '.confirmation-page' store: true transitions: # Monitor loop - from: monitor to: evaluate trigger: complete - from: evaluate to: monitor condition: result == false trigger: timer config: seconds: 5 # Commit path (when slot available) - from: evaluate to: login condition: result == true - from: login to: select-slot trigger: complete - from: select-slot to: confirm trigger: complete - from: confirm to: capture-proof trigger: complete

Key Concept The monitor state runs every 5 seconds (lightweight), but the commit states (login through capture-proof) only execute once when a slot becomes available. This is the essence of efficient automation.

2.3 Building a Payment-Enabled Workflow

Prerequisites: Completed Tutorial 2.2, x402 wallet setup

This tutorial demonstrates how to integrate micropayments into your agent workflows using the HTTP x402 protocol. You'll build an agent that can pay for priority access to a service.

Setting Up x402 Payment

states: - id: request-access action: http.request config: url: https://api.service.com/priority-access headers: Accept: application/x402+json - id: handle-payment-required action: x402.pay config: wallet: '{{secrets.wallet_key}}' max_amount: 0.50 currency: USDC - id: confirm-access action: http.request config: url: '{{payment_response.confirmation_url}}' headers: Authorization: 'x402 {{payment_response.token}}'

x402 Protocol HTTP x402 is an emerging standard for internet-native micropayments. When a server returns a 402 Payment Required status, it includes payment requirements. The client can then automatically fulfill the payment and retry the request with the payment proof.

3.1 How to Configure Agent Authentication

Most agents need to authenticate with target services. Latchwork provides secure credential management through its secrets system.

Step 1: Store Credentials Securely

latchwork secrets set visa-portal.username Enter value: ******** latchwork secrets set visa-portal.password Enter value: ********

Step 2: Reference in Agent Configuration

states: - id: login action: browser.fill config: selectors: '#username': '{{secrets.visa-portal.username}}' '#password': '{{secrets.visa-portal.password}}' submit: '#login-button'

Step 3: Configure Session Persistence

session: persistence: cookie-jar cookie-jar: name: visa-session ttl: 3600 # 1 hour

Security Best Practice Never hardcode credentials in agent.yaml. Always use the secrets system. Credentials are encrypted at rest and only decrypted in the execution environment.

3.3 How to Implement Human-in-the-Loop Gates

Some situations require human judgment. Latchwork's human-in-the-loop gates pause execution and wait for user input.

CAPTCHA Handling

states: - id: detect-captcha action: browser.detect config: selector: '.g-recaptcha, .h-captcha' - id: solve-captcha action: human.gate config: type: captcha timeout: 300 instructions: 'Please solve the CAPTCHA to continue' - id: resume action: browser.continue config: wait_for: '#booking-confirmation'

Approval Gates for Sensitive Actions

states: - id: before-payment action: human.gate config: type: approval title: 'Confirm Payment' message: 'Agent wants to pay ${{amount}} to {{merchant}}. Approve?' options: - label: 'Approve' value: approve - label: 'Deny' value: deny - label: 'Approve Always' value: approve-always

5. Explanation

Understanding-oriented discussions that illuminate Latchwork's concepts and design decisions

5.1 Understanding the Monitor-Commit Pattern

The monitor-commit pattern is one of Latchwork's core innovations, addressing a fundamental inefficiency in traditional automation approaches.

The Problem with Naive Automation

Consider booking a visa appointment. The naive approach would be to repeatedly attempt the full booking workflow: login, navigate, check availability, fill forms, submit. This is wasteful because:

  • Each full attempt consumes significant resources (compute, time, API calls)
  • Most attempts fail because slots are rarely available
  • The expensive parts (form filling, payment) are done even when unnecessary

The Monitor-Commit Solution

Latchwork separates the workflow into two phases:

Monitor Phase: Lightweight, frequent checks that determine if conditions are right for action. This might be a simple HTTP request or a quick page scrape. It's designed to be cheap and fast.

Commit Phase: The full, expensive workflow that only executes when the monitor detects the right conditions. This includes authentication, form filling, payment, and confirmation.

Economic Impact

In a typical scenario, an agent might check 1,000 times before a slot becomes available. With monitor-commit:

  • Monitor cost: 1,000 checks × $0.0001 = $0.10
  • Commit cost: 1 execution × $0.50 = $0.50
  • Total: $0.60

Without monitor-commit, each check would be a full execution: 1,000 × $0.50 = $500. The pattern reduces costs by 99.9% while maintaining responsiveness.

5.2 The Trust Layer: Staking and Validation

In a decentralized system where agents execute tasks on behalf of users, trust is paramount. How do you know an agent will do what it promises? How do you resolve disputes? Latchwork's trust layer addresses these questions through economic incentives and cryptographic verification.

Staking: Putting Skin in the Game

Agent developers stake tokens as collateral. If an agent fails to complete a task or behaves maliciously, the stake can be slashed (partially or fully forfeited). This creates a strong incentive for:

  • Building reliable, well-tested agents
  • Accurately representing agent capabilities
  • Maintaining and updating agents as target sites change

Validation: Independent Verification

Validators are independent nodes that replay agent executions to verify outcomes. They check:

  • Did the agent follow the declared state machine?
  • Are the proof artifacts (screenshots, logs) genuine?
  • Did the claimed outcome actually occur?

5.3 Session Isolation and Security

When running agents that handle sensitive data (credentials, personal information, payment details), security is critical. Latchwork's session isolation model provides defense in depth.

The Capsule Model

Each agent execution runs in an isolated "capsule" with the following properties:

  • Ephemeral: Created at execution start, destroyed at completion
  • Isolated: No access to host filesystem, network restricted to allowlist
  • Stateless: No persistence between executions unless explicitly configured
  • Auditable: All actions logged with cryptographic hashes

5.4 Economic Model and Incentive Design

Latchwork's economic model is designed to align incentives across all participants: users, agent developers, validators, and infrastructure providers.

Payment Flow

When a user requests a task:

  • User deposits payment into escrow
  • Agent executes the task
  • Validator verifies successful completion
  • Payment is released to agent developer
  • Validator receives verification fee
